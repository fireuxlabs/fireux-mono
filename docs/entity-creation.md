# Entity Creation Canon

Entity creation belongs to the entity stack. The public seam is `useXCreate()`,
and callers should use named create functions that describe what storage shape
is being created.

## Create Family

`Create` is the operation family. Storage location and input source are
descriptors, not separate operation families.

```text
Create
├─ root
├─ scoped
├─ both
├─ provider-backed
└─ provisioned/server-backed
```

## Storage Shapes

Models should declare their storage shape beside their field model. This makes
CRUD seams obey the model instead of rediscovering storage rules each time.

Example:

```ts
export const AppStorage = {
  shape: 'public/root',
  path: 'apps/{appId}',
  collection: 'apps',
  idParam: 'appId',
} as const
```

### Root

The entity exists as its own canonical record.

```text
kitchens/{kitchenId}
suppliers/{supplierId}
portfolios/{portfolioId}
projects/{projectId}
places/{placeId}
```

Root records may be public or private. `root` is storage language; `public` is
route, rendering, or publishing language.

### Scoped

The entity exists only under a parent record.

```text
conversations/{conversationId}/messages/{messageId}
apps/{appId}/kitchens/{kitchenId}/mise/{miseId}
apps/{appId}/portfolios/{portfolioId}/tasks/{taskId}
```

Scoped records should not pretend to be public/root entities unless they are
later promoted into their own root model.

### Both

The entity has root identity plus an app-scoped overlay.

```text
kitchens/{kitchenId}
apps/{appId}/kitchens/{kitchenId}
```

The root record is the thing. The app overlay is the app's operating context,
membership, permissions, and console state.

For console-backed entities, use this naming:

```text
createX        -> root record only
createXConsole -> root record plus app overlay
```

Examples:

```text
createKitchen        -> kitchens/{id}
createKitchenConsole -> kitchens/{id} + apps/{appId}/kitchens/{id}

createSupplier        -> suppliers/{id}
createSupplierConsole -> suppliers/{id} + apps/{appId}/suppliers/{id}

createPortfolio        -> portfolios/{id}
createPortfolioConsole -> portfolios/{id} + apps/{appId}/portfolios/{id}

createProject        -> projects/{id}
createProjectConsole -> projects/{id} + apps/{appId}/projects/{id}
```

## Input Source Descriptors

### Provider-Backed

The create is fed by an external or sibling provider result.

Examples:

```text
Place from Google Places data
Kitchen from Place data
```

Provider-backed create should still write the same root/scoped/both storage
shape. The provider is the source of the payload, not a storage family.

### Provisioned Or Server-Backed

The create needs storage, upload, server authority, API mediation, or a
provider result before the final record is complete.

Examples:

```text
Go QR uploaded document create
Product provider/provision flow
server-authority cross-app create
```

Provisioned create still belongs under `useXCreate()` or an app/tool-owned
create seam. It should not create a new entity family.

## Payload Rule

Create payloads should be light.

Write only:

- fields supplied by the create input
- fields supplied by a trusted provider result
- fields generated by the create seam, such as a slug
- required defaults that are true at creation time

Do not write empty future-edit fields just because the model has them.

Example for a place-backed Kitchen root:

```ts
{
  app_scope_state: 'root_only',
  app_scope_app_id: '',
  place_id,
  slug,
  name,
  short_name,
  short_address,
  formatted_address,
  image_url,
  show: false,
  is_test_kitchen: false,
  currency_code: 'CHF',
  currency_format: 'dash'
}
```

Fields such as `tagline`, `opening_hours`, `language_settings`, and richer
profile copy belong to later update flows unless they are genuinely known at
creation time.

## Read Families

After Create, the next CRUD family is Read.

Read has two stored-read operation shapes and one composition seam:

```text
Read
├─ fetch
├─ collection
└─ interface
```

Use the standard entity names:

```text
useXFetch      -> read one stored record
useXCollection -> read many stored records
useXInterface  -> compose and project read shapes for surfaces
```

Read also uses the same storage-location descriptors:

```text
root
scoped
both
```

Examples:

```text
useKitchenFetch(id)          -> root kitchen read
useKitchenCollection()       -> root kitchen collection read
useKitchenInterface().surface -> root/place/overlay surface composition

useKitchenMiseCollection()   -> scoped kitchen child collection read
useConversationMessageFetch  -> scoped child single read

useKitchenConsole()          -> both/root plus app overlay operating read
```

`useXInterface` may meld already-read records into a stable surface shape. It
must not fetch hidden data by itself. Fetch and collection own transport;
interface owns composition and projection.

Read can also have composed shapes:

```text
hydrated
provider-backed
server/API-mediated
```

Those are read descriptors, not entity families.

Hydrated reads combine records at read time. They must not be treated as stored
families.

Provider-backed reads load or enrich from a provider but still return an entity
read shape.

Server/API-mediated reads use a Nuxt API route when authority, privacy, storage,
provider access, or public-safe response shaping requires the server.

## Mutation Families

After Read, mutation seams stay entity-owned and boring.

```text
Mutations
├─ useXUpdate
├─ useXPublish
└─ useXDelete
```

`useXUpdate` patches an existing stored record. It may validate fields owned by
the entity, such as a public slug, but it should not create records, hydrate
read shapes, or build UI projections.

`useXPublish` is only for entities with explicit public/indexable publication.
It owns readiness checks and route meaning, then delegates the write mechanics.
Private-by-default entities, such as kitchen recipes, should add publication as
an explicit state/seam when public recipe routes are real.

`useXDelete` owns the entity removal posture. The entity decides whether delete
means hard delete, archive, unpublish, or scoped relationship removal. That
choice belongs in the entity seam, not in the low-level Firestore primitive.

Mutation helpers should use model storage metadata for collection paths:

```ts
await updateDocument(KitchenStorage.rootCollection, id, patch)
await deleteDocument(KitchenStorage.rootCollection, id)
```

Scoped placement records should stay lightweight. For example, Dish owns food
truth, while MenuItem only places a Dish on a Menu section.
