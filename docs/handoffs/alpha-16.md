## Architecture and ownership

**Nuxt assembles. Core connects. Firestore describes. Nuxt renders.**

1. **Assembly and deployment inputs.** Blank, Misebox and Holzworm explicitly extend `fireux-core/layer`, register `@nuxt/ui` and select their local CSS. Their `nuxt.config.ts:1–11` (Misebox through line 17) declares the running App ID and trusted private deployment scope. The Core package export loads `packages/core/fireux-core/src/nuxt.config.ts:1–19`. Nuxt merges fail-closed declarations and discovers the layer components and Nitro routes. All three existing generated `.nuxt/components.d.ts` and `.nuxt/types/nitro-routes.d.ts` resolve to Core. Any App using the layer currently registers its server routes, including protected ones even when no sign-in UI is present. App manifests use native dotenv flags. Environment values take precedence over local `.env` and tracked `env.defaults`. Demo IDs are guard expectations. They select neither database nor host. App and Ecosystem records own published facts. Holzworm's product content and theme are authored App presentation.
2. **Trusted connection and self identity.** `packages/core/fireux-core/src/server/utils/firebase-admin.ts:5–32` uses server project/database configuration. It uses the Admin registry and ADC mechanisms directly, enforces a matching demo project and loopback emulator or an explicit development-only live opt-in, and resolves the named database. The self route `src/server/api/app.get.ts:6–15` takes only configured identity, validates kebab-case and calls `src/server/app/detail/read.ts:6–23` for one exact `apps/{id}` read. Active status and private scope are server checks. Only confirmed standalone with absent membership fits the scope-free path. `src/server/app/read-app-document.ts:66–113` checks the stored contract and projects public fields. Database supplies the document ID. Private context and stamp actor IDs stay server-side.
3. **Native SSR and rendering.** `src/app/components/App/Detail.vue:1–25` owns a keyed `useFetch('/api/app')` and exposes the same result to Blank and Misebox via slots. Their heading and Detail card share it. Holzworm `projects/fireux/holzworm/app/layouts/landing.vue:1–26` owns the equivalent native fetch in its layout, uses it for navigation and title, and leaves catalogue access intact on failure. Nuxt carries the fetched payload into hydration. Earlier browser checks proved no duplicate browser acquisition. No shared store or general fetch wrapper exists.
4. **Discovery.** Blank and Misebox choose to show peers after acquiring a self record with membership. `src/server/api/apps/index.get.ts:5–11` and `src/server/app/collection/read.ts:6–35` independently enforce private scope, active status, stable document order and cursor. Its result may include self, which the client conceals. Explicit peer lookup `src/server/api/apps/[id].get.ts:5–11` is independently bounded and shares the exact reader. The UI does not invoke this peer detail route. Misebox alone renders separate `/api/ecosystem` data via `src/server/ecosystem/detail/read.ts:18–39`. That record is description for its own view. Peer membership comes from the App relationship. Self depends on neither route.
5. **Identity intersection.** Misebox uses `projects/misebox/misebox-app/app/components/MiseboxAuth.client.vue:64–193` for optional browser SDK sign-in. It sends a bearer token for independent protected User and AppUser reads. `src/server/utils/require-firebase-user.ts:6–34` verifies with the configured Admin app before applying operation-specific rules. User is a person profile, AppUser is one membership, and count requires the current stored admin/dev role. Creation and join remain separate, dev-emulator-only transactions. Public acquisition uses no Auth, User or AppUser. The dependency direction is read securely from the same configured target, with Auth outside the virtual App document path.

For the relative imports and known native discovery and endpoint edges, a static walk resolved 52 authored source/config nodes and 68 edges with no cycle. This is a bounded source finding, not a claim about every third-party dependency or all dynamic runtime interactions.

2. Decide if development acquisition diagnostics should live at the App boundary or stay current. Clarify what the inspector snapshots mean and retain provenance. Consider SSR owner clarity using the two existing patterns without adding a helper as a default.
3. Take bounded naming and contract typing cleanup once response behavior is fixed. Reuse standard Nuxt/Vue/Firebase mechanisms.
4. Before expanding identity, confirm the intended difference among User, AppUser self-read, scoped join and admin count. Correct the client ref guard separately under authorization. Keep server authority and transactional guarantees.
5. Treat production delivery as an independent decision and prerequisite for release. Hosting/Firestore deployment ownership and live bindings need approved evidence. No release, live lookup or role policy expansion belongs in this audit.
