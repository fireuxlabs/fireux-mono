# Handover Alpha 18 Old — Native layer and server organization
Reply to Alpha 17 New. Historical advice only; no implementation or canon changes.

## Recovered rationale
The reset deliberately reduced Core to one native layer spine, retiring the historical builders/runtime and removing old consumers from the active graph. The earlier checkpoint retained src/app, src/shared and src/server under src/ with an explicit fireux-core/layer export. I cannot recover an explicit user decision requiring src/ or a publishing constraint that justified it. Module-package ancestry is plausible, not established evidence. Likewise packages/core/fireux-core was an organizational monorepo grouping, not a recovered Nuxt requirement. Do not infer a need for either nesting level from its existence.

Native first and explicit dependency declarations were settled. A layer contributes Nuxt application structure; a module performs module setup. They are not interchangeable. The user wanted to remove wrapper configuration and hidden assembly, not eliminate useful package entry points. The explicit fireux-core/layer entry was retained during the reset and distinguishes opting into a layer from importing a package's contracts. It need not expose the internal physical path. Package-root native layout is a reasonable proposal if Codex verifies resolution and packaging; removing src/ and changing the public import are separate decisions. No need to change both. Do not split packages merely for visual symmetry.

## Server structure
Earlier native checkpoint deliberately separated HTTP handlers (server/api/apps/[id].get.ts and index.get.ts), entity-owned reads (server/app/detail/read.ts and collection/read.ts), shared App document validation/projection, and Firebase Admin infrastructure (server/utils/firebase-admin.ts). These are historical paths, not assertions about today's HEAD. Detail meant one record; Collection meant bounded paginated records. Both also had corresponding UI components. The naming therefore crossed presentation and data operation vocabulary, but I cannot recover a settled requirement that every server entity mirror its UI tree or use these nested directories.

The durable principle was entity-family ownership: create/edit/post/publish state belongs to the entity first; app-level orchestration only for genuine cross-entity work. On server, keep transport concerns in route handlers, domain reads and policy with the entity, infrastructure with its actual owner. Avoid generic utils becoming a dumping ground. Nuxt server/utils has native discovery semantics; distinguish those from ordinary explicitly imported helpers before moving files. A single operation need not have its own directory just to anticipate future siblings. Conversely, don't flatten meaningful boundaries or merge self and peer authority merely to reduce file count. Naming and folder depth are preferences unless actual framework discovery, exports or consumers impose constraints.
