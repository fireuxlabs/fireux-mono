## Dependency and coupling evidence

- The component coordinates two independent reads in parallel after one token acquisition. AppUser read does not need a User read. The first-join action does. The current combined screen requests both every time a user signs in. Authenticate-only Apps should not make those reads just because the reference panel does. Profile and membership reads also have similar headers, abort checks, and 404 handling. Keep the local orchestration explicit initially. Cleanup and stale-result guards are meaningful responsibilities.
- `readProfile` currently mutates provisioning visibility by decoding the development diagnostic header. This ties UI availability to a read response and a literal database name. Keep it as a development eligibility hint in a move. Server authority remains in the guarded routes. No new discovery endpoint is warranted in this slice. Browser handle/length constraints repeat the server rules for form UX. Preserve independent server enforcement.
- Existing local issue to review separately: client line 212 checks the `canProvision` ref object, while join line 251 checks `.value`. The template and trusted server guards remain separate. This source audit made no behavior change.
- The same version pair is sent for the two hardcoded Misebox legal links. Let Apps supply links only where the current approved versions still identify the displayed documents. If different Apps require different versions, the server-owned policy and authoritative documents need a separate decision before reuse. No browser-supplied versions can replace the validator.
- Core already registers five protected handlers. `GET /api/app-users/count` has no Misebox browser caller and retains its stored-role authority. Providing the existing server routes and installing/mounting a browser capability are separate. The audit proposes no route registration, production-write or authorization change.
- Blank and Holzworm have no direct `firebase` browser dependency or browser Auth config. Core has Firebase Admin and h3, plus Nuxt/UI/Vue peers, with no browser SDK dependency. The root package directly declares `firebase` at `package.json:102`. Node therefore already resolves that SDK from all three Apps and Core through the parent workspace. This cannot prove a proposed package boundary. In the existing compiled client JS, Firebase Auth markers were found in Misebox and absent in Blank and Holzworm. This is a read-only baseline, not a test of the proposed layout.

## Proposed reusable arrangement

Reuse a single Core-owned, client-only reference component, for example `packages/core/fireux-core/app/components/Auth/Google.client.vue`. Nuxt can discover `<AuthGoogle>` when an App explicitly mounts it. Keep its state and requests local and reuse the already discovered `UserDetail` and `AppUserDetail` views. The existing contracts stay in `shared/user/` and `shared/app-user/`; the existing validated operations and routes stay under `server/`. App config, legal links, page placement, and inspector stay with the App. The shared component imports the consent constant relatively from the same package as the validator. Its public component name is a Nuxt-layer interface and needs no per-file package export.

Another App would keep `extends: ['fireux-core/layer']`, declare the browser SDK and its Firebase Web runtime config when it adopts the UI, mount the component, and opt into profile and/or membership sections with plain component inputs. Sign-in alone needs neither protected app-data read. Preserve current Misebox choices by selecting both sections. Join keeps its current User, App, ecosystem and emulator requirements. Apps that want custom presentation already have native Firebase plus the protected HTTP contracts and can reuse the two detail views today. They currently would have to supply their own orchestration or copy the reference for an equivalent UI. Extract a composable only when a real second presentation needs the same lifecycle without the component.

Prove the one-component path in a clean packed consumer first. A Vue client-only suffix governs rendering. It alone does not prove dependency-resolution or bundle isolation. Evaluate an optional Firebase peer and explicit dependency only in opting-in Apps, with no mandatory browser dependency in the base layer. If the normal component scan pulls SDK-bearing source into non-opt-in builds, consider a small optional native layer inside the same package, outside auto-scanned `layers/`, with its own config and component. A deliberate layer entry is justified only by that demonstrated boundary. If workspace/packed SDK resolution still fails, keep the tiny Firebase SDK integration App-owned and share the generic UI/route coordination using the actual needed inputs. Do not fix peer resolution with ambient root deps, aliases or automatic plugins. No package, module, provider or store is required by current evidence.
