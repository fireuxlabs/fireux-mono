## Recover the actual manual audit
Old and the developer already reviewed this exact historical Misebox config field by field before the context reset. Alpha 7 is substantially aligned, with the following useful corrections and qualifications.

1. Identity: initially we considered reducing ecosystem/projectId/ecosystemId/id to two identifiers, then explicitly revised that idea. Repository project grouping (projects/<group>/<app>) is organizational; ecosystem membership is functional. Go QR could be organized under FireUX without belonging to the FireUX ecosystem. Firebase project ID is a separate infrastructure identifier (Misebox example misebox-78f9c, named database misebox). The old projectId's runtime necessity was never established. ecosystem and ecosystemId appeared redundant; id identifies the App, with appId preferred for clarity in config. Do not collapse distinct concepts just because their strings happen to match. Do not retain an organizational projectId in runtime unless a real consumer warrants it. Keep any necessary trusted server ecosystem restriction pending the security decision.

2. context: the developer explicitly wanted a better AI-facing ship-level description, not a snapshot of current progress. We drafted a description of the intended connected hospitality ecosystem, covering kitchen management, ingredients, recipes, menus, recruitment, procurement, websites, ordering and customer engagement, with connected workspaces and individual products. Later we agreed long development context belongs in repository documentation, not generic public metadata or startup configuration. A private stored App context may have a concrete use, but none was established in this audit. Do not lose product intent; do not expose aspirational features as already shipped.

3. domains/profiles: the developer suspected these arrays were an attempt to connect memberships and domains, and explicitly favored removing them from the active App foundation and rebuilding only when required. No actual historical composition, authorization or discoverability consumer was established. Preserve domain/profile data and useful behavior separately; do not recreate a generic registry by default. AppUser membership, user profiles and domain authority are distinct. The old arrays are not evidence of a necessary architecture.

4. modules/extends: native Nuxt modules perform setup; layers extend configuration and application source. Both are legitimate native assembly mechanisms, not interchangeable. The developer asked to audit the legacy wrapper rather than assume its responsibilities necessary. The reset direction is native defineNuxtConfig and explicit Core layer, not defineFireuxEcosystem. Any surviving wrapper behavior must justify itself through a concrete current requirement; no compatibility wrapper by default. Do not restore all old modules/layers merely to recreate the historical config. Their feature options may be legitimate when those features return.

5. Other fields: name and shortName serve distinct display purposes, shortName optional with full-name fallback; both belong to authoritative App metadata. contactEmail is optional public contact metadata, not a credential. homePath '/' was explicitly flagged as redundant with native Nuxt index routing; do not move it into Firestore by default. Only retain a field if a genuine configurable destination is demonstrated. Role is one stored classification (global/tenant/standalone), not a module selector or authority grant. SEO was deliberately deferred until product readiness, except preserving architectural prerequisites such as SSR and native routing. staticPaths is a removal candidate if unused; genuine prerender route lists belong in native build configuration, not App metadata. Do not disable useful SSR in the name of removing SEO.

## Illustrative minimum, not a new contract
Native defineNuxtConfig with explicit modules and extends actually needed, and runtimeConfig declaring a trusted running App ID and Firebase connection settings supplied by environment. Retain the current private ecosystem constraint until an equivalent boundary is agreed and verified. No name, shortName, role, domain/profile registry, generic homePath or AI context in the running App config by default. Exact nesting, names, public Firebase client settings and scope remain for Codex evidence; do not copy this conceptual shape as implementation. Firestore apps/{appId} owns public metadata, with explicit safe projection. A document's role or membership is not itself authorization. The deployment self selector must not be caller-controlled. Separate self and peer trust requirements without assuming a new route or abstraction is mandatory.

## What should survive the cull
Native routing/SSR, Firebase routing and credentials, explicit assembly, safe public field projection, active status and scope checks, bounded peer lookup, domain features when required, and the distinction between private AI context and public descriptions. Preserve historical functionality in Git and migrate consumers to the new foundation, not the reverse. Do not delete Firestore records or live data. Earlier manual audit was discussion, not a verified local source trace. Alpha 7 reports Alpha 6's evidence; Old has not independently inspected current local HEAD. Codex should verify model support for contact metadata and optional membership, actual consumers and security implications. No further architecture decision from Old is necessary unless New identifies a genuine gap.
